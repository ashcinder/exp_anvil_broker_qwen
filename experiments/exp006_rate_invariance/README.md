# exp006 · 注入速率不变性 + 机器吞吐上限（50 broker × 4 分片 × 1 万笔）

**测什么**：把 exp005 选定的进程基底放到真实负载下，回答两个问题：
1. 注入速率会不会改变理论结果？——同一批 CTX、同一 LPT 指派，按逻辑块以多档
   `ctx_per_block` 注入，看路由决策与守恒会不会随速率漂移。
2. 这台机器能扛多大吞吐？——扫一列速率，找墙钟吞吐随速率上升而进入平台的位置。

这是 M3 逻辑时钟的第一次压力验证：到达【只被新区块驱动，绝不被墙钟驱动】
（父进程到达监视器读 min(各分片块高)，released = 块龄 × 速率）。审计 F1 说旧代码
把负载绑在机器速度上、结果跨机器不可比；本实验正面检验新平台是否免疫。

**结构（每个速率档）**：
- 4 个 anvil 分片（1 s 块）；
- 1 个 coordinator 进程：单一签发账户，代铸所有 relay 的 mint 段（账户单写者）；
- 50 个引擎进程（exp005 冠军基底）：各自的 NonceManager / Web3 连接；
- 到达监视器线程：按块高推进 `released` 计数器，引擎 `pump()` 读它决定放行到哪。
- 引擎内路由：本 broker dst 侧可用 ≥ v ⇒ broker 路径；不足 ⇒ relay 兜底
  （burn 段引擎用 sender 账户自签，mint 段经队列交 coordinator 代铸，回执异步返回）。

**判据**：
- **H-R1 速率不变性**（退出码判据）：路由决策指纹 `sha256(ctx_id→route 按 arrival_pos 排序)`
  在**所有**速率档完全相同。机理：决策在 pump 时按余额定下（到达序升序、金额驱动），
  与墙钟/超时无关。若成立 ⇒ 注入速率不影响逻辑结果，审计 F1 被结构性根治。
- **H-R2 全负载守恒**（退出码判据）：每档全局净和 = 0 wei（gasPrice=0，钱不凭空生灭，
  即使高负载有超时也成立）。
- **饱和信号**（report，不判负）：某档 `failed>0` 或 `mirror_mismatch>0` = 该速率已超机器
  能力（burn/ mint 段落块超过超时阈值）。这是要找的上限证据，不是 bug。
- **吞吐曲线 / 上限**：`throughput_ctx_per_s` vs rate；平台值 = 这台机器的 CTX/s 上限。

**与 exp001/002/005 的口径关系**：exp001 是单 broker 双路径静态对照，exp002 是单 broker
耗尽序列，exp005 是三容器吞吐对比（一次性全量释放）；exp006 首次引入【按块到达 +
50 并发 + 速率扫描】，是三者通向 M3/M6 的合流点。字节/段数类结论仍按 exp001 实测口径。

**运行**：
```bash
python -m brokerlab doctor --config experiments/exp006_rate_invariance/config.yaml
python run.py                                            # 4 档 × 1 万笔，后台 ≈ 15–25 分钟
python run.py --set exp.rates=5,20 --set exp.ctx_per_broker=3 --set exp.pool_scan=400  # 冒烟
```

**效度声明（写死在 README，跑完补数据）**：
1. coordinator 是全局单点：relay 占比高时它会成为串行瓶颈，届时"上限"含 coordinator 分量；
   正式档用高垫资让 broker 路径占主导来隔离这一点，dev（bal=1）另测 coordinator 分量。
2. 静态指派 + 无动态匹配：broker 间的实时负载均衡属 M3，本实验按 exp005 的 LPT 静态箱。
3. 6 核 15 GB 共享机：吞吐上限是本机口径，换实验室机器需重测（doctor 已给硬件行）。
4. anvil 单节点 RPC 与各引擎并发共享同一序列化点，是吞吐的物理来源之一。

- **H-R1 速率不变性 = True（核心结论）**：决策指纹 `cd7a0686e6a1133a` 在 25→300 四档
  逐位相同，served/relay/失败/净和全部一致。吞吐从 24.6 拉到 121.6（5×），
  逻辑结果一丝不变。审计 F1"负载绑机器速度→结果不可比"在新平台被结构性根除，
  且在 1 万笔、双路径（broker+relay）混合下成立。
- **H-R2 全负载守恒 = True**：四档净和均 0 wei，零失败、零镜像漂移（RSS 峰值 3867 MB）。
- **机器吞吐上限 ≈ 120 CTX/s**：吞吐在 rate 150 达峰（121.6），rate 300 反而回落到 114.2
  ⇒ 拐点在 75–150 之间，平台 ≈120 CTX/s。超过平台再加注入速率，吞吐不涨。
- **代价是延迟不是吞吐**：hops 四档都 ≈2.0 ⇒ 链上入块没变慢；p95 从 2.1 s（rate75）
  涨到 18.4 s（rate300）纯粹是 Python/RPC 侧的排队积压（到达快过排空）。这正是
  "积压是导出指标、到达轨迹与机器无关"（计划逻辑时钟）的实测体现。
- **推荐本机上限参数档**（50 broker × 4 分片）：
  - 追吞吐：rate=150 CTX/块，≈120 CTX/s，p95 7 s，可接受；
  - 要干净延迟：rate=75，≈70 CTX/s，p95 2.1 s（几乎无排队）；
  - 硬上限：rate>150 无吞吐收益，rate 到 300 仍零失败（超时阈值 150 s 吸收），
    真正出失败点在 300 之上（未测）。RSS/核数远未到顶，瓶颈是 anvil RPC + 引擎并发轮询。
- 三面板图 `figs/exp006_rate.png`：(a) 吞吐平台 (b) e2e 均值/p95 随速率超线性上升 (c) 墙钟。

**结论**：注入速率不影响理论结果（决策/守恒跨 5× 速率逐位不变）；这台机器在
50 broker × 4 分片下扛得住 ≈120 CTX/s 的持续吞吐，rate ≤150 为零失败安全档。
