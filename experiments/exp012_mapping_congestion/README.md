# 实验 12：地址映射集中度与跨分片容量压力

研究问题：固定资金、注入负载和分片容量时，将地址空间逐渐集中到一个或两个分片，
Plain、Valve、现有 EWMA 自适应补充策略的 Relay、额外再平衡开销、吞吐和入块等待如何变化？
用户所称 RWMA 在本实验中沿用项目已经实现的 EWMA (`topup` + 半衰期) 方案，未新增估计器。

## 后缀桶映射

设地址整数为 `n`，读低 `b` 个二进制位：`bucket = n & ((1 << b) - 1)`。

```python
if bucket < 16:
    shard = bucket
else:
    shard = hotspots[(bucket - 16) % len(hotspots)]
```

4 位时只有 0～15 桶，恰好等价于原来的 `int(address,16) % 16`。
5 位增加 16～31 桶，6 位增加到 63 桶；新增桶分配给预先固定的热点分片。
所有 16 个分片始终保留原始桶。发送方和接收方使用同一函数；同一真实地址在一个场景内
始终归属同一个分片。各档是独立布局，不模拟运行中迁移，也不计迁移费用。

| 场景 | 位数 | 热点 | 理论每个热点的地址占比 | 理论每个热点的跨片段占比* |
|---|---:|---|---:|---:|
| uniform4 | 4 | 无额外热点 | 每片 6.25% | 每片 6.25% |
| one_hot5 | 5 | S0 | 53.125% | 35.417% |
| one_hot6 | 6 | S0 | 76.5625% | 43.750% |
| two_hot5 | 5 | S0、S1 | 各 28.125% | 各 24.410% |
| two_hot6 | 6 | S0、S1 | 各 39.0625% | 各 34.428% |

*理论值假设地址后缀均匀、两个端点独立。真实 trace 存在重复地址和热门端点，以审计实测为准。
仅增加位数再 `% 16` 不会改变分片；真正产生集中的是新增桶的非均匀分配。

地址占比与跨片段占比不同：当两个端点落在同一热点，就变为片内交易。
若地址分布为 `p_s`，在独立假设下，跨片率是 `1 - Σ p_s²`，
条件于跨片后的端点占比为 `p_s(1-p_s)/(1-Σ p_s²)`。
一笔 CTX 在源、目的各消耗一段，单个分片的跨片段占比不超过 50%。

## 数据选择与公平性

1. 原始 CSV 按文件顺序读入，选前 50,000 条合格候选；记录原 CSV 行号、块号、时间戳。
   成功、有有效端点、金额在范围内、非创建交易；允许合约端点。
   同时排除模拟账户碰撞和重复交易哈希。此时不按分片过滤，保留可能的片内交易。
2. 对同一候选池分别施加五种映射，再排除该映射下的片内交易，保序取前 10,000 条 CTX。
   候选不足时直接报错，需增加 `exp.candidate_count`；不静默缩短实验。
3. 每个场景固化一份 `workload.json`，三种方法、三次重复重放完全相同的交易、金额、顺序、映射。
   每次载入校验 SHA256、行数、身份、分片、金额和账户索引。
4. 每个方法使用全新链、相同初始资金。同场种子相同；每次重复轮转方法与场景顺序，减轻运行顺序影响。

**不同映射档位的 CTX 集合不完全相同**，因为片内过滤结果不同。固定的是候选池、
选取规则、CTX 数量和目标 CTX 注入率；不是相同原始交易或相同原始时间跨度。
各档的金额矩阵、金额总量、原始区间、片内率都输出，不能把跨档差异完全归因于拥堵。
本实验条件于“跨片需求”，片内交易不占用模拟区块。因此它研究的是跨片子系统容量压力，
不是完整重放整个以太坊业务负载。需要完整系统拥堵实验时，须另加片内执行管线。

实验 12 不使用 exp003 的 sender-group 大小过滤，避免提前删除真实热点；
因此不能与旧 exp008 的结果当作完全同一负载对比。模拟账户仍使用原有
`user_base_index + n % num_users` 的压缩规则：多个真实地址可能共用模拟账户，
并受 `sender_window=8` 限制。低实际注入率可能来自发送端或主机，不一定来自链满。

## 指标与判读

- 映射集中度：每片地址数、源/目的笔数、跨片段占比、HHI。
- 流动性偏斜：金额矩阵、每片用户净流入、broker 潜在净变化，及按到达位置切分的 20 逻辑块窗口统计。
  净偏斜系数为 `Σ |用户净流入_s| / (2 × 总金额)`。
  这是全部请求的潜在资金压力；实际 broker 余额只受 broker 成功服务的 CTX 和再平衡影响。
- 容量：实际每块 gas 使用率、满块比例；源腿/目的腿的入块跳数 P95 和超过 1 块的比例。
- 机制：Relay 数/比例、TDR 事件/转移/链上段数、总链上段数、吞吐、服务延迟 P95、实际注入率、coordinator backlog。
- 完整性：无丢失/重复、无失败、账本与链上相同、总资金守恒、桥预算与 burn 对账等原管线检查。

区块统计在交易服务计时结束后只读采集，统计第一笔至最后一笔 CTX 确认的共同已出块区间，
包含该区间的 TDR gas；独立链高度有差异时，末尾截到最慢链高度，并记录 `last_ctx_block`。
后续 TDR 收尾不在该容量窗口内，但计入 TDR 段数与单列收尾时间。
`e2e_secs` 是现有管线的服务阶段计时，不包含全部到达后等待；应结合 backlog 解读。

判断实际拥堵，需要同时看忙片是否出现持续满块、入块跳数/排队是否增长、实际注入是否达到目标。
仅有高地址占比或 `max_target_capacity_ratio > 1` 是压力预测，不是已发生拥堵的证据。
单热点和双热点是两组拓扑，各自比较 5→6 位；不要把五档强行当作一条严格单调曲线。

EWMA 的研究收益是降低 Relay 并量化额外搬运与吞吐代价。这里 Plain 与 Relay/Broker 路径
每个成功 CTX 都是两段交易；降低 Relay 本身不会减少 CTX 链上段数。
TDR 还会占用区块，所以强拥堵下不保证 EWMA 优于 Plain/Valve，也不能因为未胜出就删除一场。
程序退出码只表示执行和完整性，`report.json` 保存包括负收益在内的配对结果。

## 运行

使用已有 brokerlab Python 环境及 Anvil，从项目根目录：

```powershell
cd D:\BaiduNetdiskDownload\exp_anvil_broker_qwen\exp_anvil_broker_qwen
python experiments/exp012_mapping_congestion/run.py --check
python experiments/exp012_mapping_congestion/run.py --prepare-only
python experiments/exp012_mapping_congestion/run.py
```

`--check`（同 `--dry-run`）只检查并展示配置，不创建产物、不启动链。
`--prepare-only` 会扫描真实数据、保存各档 workload 和审计表，不启动链。
默认命令重建本次输入并跑正式 45 组；不会接着调参或寻找有利映射。
已进入实验目录时可直接 `python run.py`。

先跑一轮正式规模、只比较均匀与强单热点：

```powershell
python experiments/exp012_mapping_congestion/run.py --scenarios uniform4,one_hot6 --set exp.sessions=1
```

小规模链上冒烟测试（改变 broker 数与样本量，只验证工程正确性）：

```powershell
python experiments/exp012_mapping_congestion/run.py --scenarios one_hot6 --set exp.sessions=1 --set scale.num_brokers=2 --set exp.ctx_per_broker=100 --set exp.candidate_count=2000 --set chain.base_port=13600
```

高容量对照：

```powershell
python experiments/exp012_mapping_congestion/run.py --set chain.gas_limit=30000000
```

在 `config.yaml` 中编辑 `scenarios` 可调整热点列表；支持 1、2、4、8 个热点与 4～8 位。
`balances_eth`、`valve_threshold`、`ewma_epsilon`、`ewma_half_life` 为方法参数权威输入，
启动时生成三方案 arms 和 broker 初始资金，不要仅修改 `arms`。
目标数为 `scale.num_brokers × exp.ctx_per_broker`；不同方法共享这一数量。
同一端口范围只能有一场运行，发现端口占用会报错，不会终止其他实验。

## 产物

每次写入本目录 `out/<时间戳>/`：

- `resolved.yaml`、`plan.json`、`source_hashes.json`：生效参数和实验源码版本。
- `source_manifest.json`：原 CSV 路径、大小/修改时间、过滤计数、候选池内容摘要。
- `mapping_audit.csv`：五档实测集中度、片内率、净流偏斜、目标容量压力。
- `<场景>/mapping_buckets.csv`：每个二进制桶到分片的完整查表。
- `<场景>/workload.json`、`workload_audit.json`：固定输入、候选和入选统计、流量矩阵、窗口统计。
- `<场景>/session_N/config.yaml`、`run.log`：子进程配置与完整日志。
- 下层各方法目录：原有交易/余额/TDR 文件，以及新增 `block_capacity.csv`。
- `metrics.csv`：每次每方法的原始指标；失败记录标记 `valid=false`。
- `report.json`：完整性、有效重复的中位数/范围、EWMA 相对 Plain/Valve 的逐次配对差值。

发现执行或完整性失败时停止后续场次并保留报告。中位数不包含失败场，失败场仍保留。

## 设计审查结论

该设计能检验“地址布局集中引起的跨片负载压力下，不同资金管理机制的表现”。
均匀地址映射不保证真实 trace 的净流平衡；热点映射不保证单向流。
三次路由种子重复评估同一 trace 的运行变异，不是三个独立真实时间窗口。
还存在 0.5 ETH 初始余额小于部分单笔金额的条件，审计会报告这些笔数，避免把所有 Relay 都解释为逐渐耗尽。
若要单独证明定向净流是 RWMA/EWMA 优势来源，应另做方向可控实验；
若要证明非劣性，应预先设定指标容忍界限并增加独立数据窗口，不能只看一次结果接近。

默认真实数据预检查已确认 10,000 CTX 可取满，实测最大跨片段占比分别为
7.995%、34.580%、43.070%、24.315%、33.645%；对应目标容量比分别为
0.19188、0.82992、1.03368、0.58356、0.80748。这些是输入负载审计，不是链上拥堵或算法胜出的结论。
